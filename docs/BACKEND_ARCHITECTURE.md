# Архитектура backend: системный анализ

Дата анализа: 2026-09-03. Сервис предназначен только владельцу и его семье;
ожидается менее 50 пользователей, платных подписок, ролей и биллинга нет.
Поддерживается только EPUB: PDF намеренно исключён, поскольку его фиксированная
пагинация не даёт качественно менять размер шрифта и сохранять позицию для
задачи ридера.

## Сценарии и последствия требований

| Требование | Решение |
| --- | --- |
| Несколько членов семьи | Отдельные аккаунты; словарь, прогресс и список добавленных книг личные. Каталог EPUB общий для семьи. Нет админ-панели, подписок и публичного доступа. |
| Загрузка и чтение EPUB | Загруженный EPUB попадает в общий семейный каталог. Файл и обложка лежат на диске сервера в приватном volume, в PostgreSQL — метаданные и подготовленный текст. EPUB преобразуется в безопасные главы с CFI-якорями. |
| Последняя позиция и настройки | В PostgreSQL хранится одна запись прогресса на пару пользователь–книга; размер шрифта — настройка пользователя. |
| Перевод слова и предложения | Словарные смыслы и примеры — локальный индекс Wiktionary; перевод предложения — бесплатный self-hosted LibreTranslate. |
| Личный словарь и подсветка | Сохраняется lemma; ридер запрашивает lemmas пользователя для текущей главы и подсвечивает совпадения. |

## Решение: простой модульный монолит

Нужен один Go-процесс `reader-api` с модулями `identity`, `library`, `reader`,
`dictionary` и `translation`. Это не микросервисная архитектура: при таком
числе пользователей она только добавила бы отдельные базы, сеть, деплой и
диагностику без полезного масштабирования.

```text
Browser --gRPC-Web--> Envoy --gRPC--> reader-api --PostgreSQL--> reader DB
                                      |                  |
                                      |                  `-> книги и обложки в Docker volume
  `--HTTP--> LibreTranslate (локальный контейнер)
```

Envoy нужен лишь потому, что браузер не умеет обычный gRPC transport; это
не второй прикладной сервис. PostgreSQL — единственная БД. Redis, S3/MinIO,
очередь, Kubernetes и отдельный worker для этой версии не нужны. Обработка
EPUB выполняется короткой фоновой задачей в том же приложении с записью статуса
в БД; при перезапуске приложение подхватывает незавершённые задачи.

Модули имеют application/use-case слой и интерфейсы к PostgreSQL, файловому
хранилищу и translation provider. Они не обращаются к таблицам друг друга
напрямую. Публичный контракт расположен в `protos/reader/v1` и версионируется.

Общий каталог не делает личные данные общими: доступ к метаданным и чтению
книги есть у всей семьи, но добавление в «мою библиотеку» фиксируется отдельной
связью пользователь–книга. Открытие книги идемпотентно создаёт эту связь, если
её ещё нет. Удаление книги из личной библиотеки не удаляет EPUB из каталога и
не затрагивает других членов семьи.

## Безопасность и эксплуатация

- EPUB — недоверенный ZIP: проверяются сигнатура/MIME, размер и коэффициент
  распаковки; XHTML санитизируется, scripts и внешние URL удаляются.
- Каталог книг — приватный Docker volume, не статический web-root. Любая выдача
  проверяет владельца книги.
- Пароли хэшируются Argon2id. Нужны короткий access JWT и отзывной refresh
  session, но отдельный OAuth/OIDC-провайдер не требуется.
- В логах нет текста книг, выбранных предложений, паролей и токенов. Достаточно
  health endpoint, структурированных логов и метрик ошибок/времени обработки.
- Бэкап: nightly дамп PostgreSQL плюс зашифрованная копия volume с EPUB в
  отдельное домашнее/облачное место. Это важнее горизонтального масштабирования.

## Когда пересматривать решение

Отдельный ingestion worker имеет смысл только если разбор EPUB заметно мешает
чтению. Object storage — если серверных дисков перестанет хватать или появятся
несколько инстансов. Внешний платный переводчик — только если качество
LibreTranslate для семейных книг окажется неприемлемым. До этих сигналов
простую схему не усложняем.
