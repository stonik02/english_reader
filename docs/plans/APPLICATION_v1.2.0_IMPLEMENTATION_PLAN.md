# План реализации требований v1.2.0

Дата: 2026-09-07.

Этот документ относится к
[`APPLICATION_v1.2.0.md`](../business_requirements/APPLICATION_v1.2.0.md).
Работы выполняются последовательно: исправления, способные повредить доступ к
книгам или данным, не смешиваются с визуальными правками. Архитектура остаётся
прежней: один Go API, PostgreSQL, локальное EPUB-хранилище, Envoy и локальный
LibreTranslate.

## Текущий статус

- [x] Пароль: регистрация принимает от 8 символов; правило проверяется и в
  браузере, и на backend.
- [x] Роли и книги: добавлены `user`/`admin`, серверное право удаления,
  лимит 10 загрузок для `user` и операторская команда назначения администратора.
- [x] Точечный UI: центрирование стрелок, одинаковая геометрия карточек,
  кнопка `+` с подсказкой для добавления слова в словарь, спокойный серый
  контур и полное отключение подсветки словаря.
- [x] Ридер: устранён ложный экран об отсутствии глав после успешного ответа.
- [x] Перевод: нормализация текста, защита от одинаковых параллельных запросов
  и один короткий повтор временной ошибки LibreTranslate.
- [x] Большие EPUB: главы разделяются только между целыми HTML-узлами, а
  прогресс сохраняется при переобработке книги.
- [x] EPUB, существовавшие на момент оптимизации, были переобработаны после
  локальной резервной копии БД; впоследствии одну из книг пользователь удалил.
- [x] Ридер: убрана синхронная обёртка каждого слова при показе главы;
  следующая глава загружается в фоне, пока читается текущая, а подсветка слов
  возвращается фоновыми порциями после первого показа текста.
- [ ] Ручная проверка desktop/touch, повторные измерения времени в браузере и
  сквозная приёмка.

## Что уже есть и что требует исправления

В коде уже присутствуют ползунки размера шрифта и межстрочного интервала,
настройки сохраняются в `user_reader_settings`; значит, сначала нужно
воспроизвести именно сбой ввода, а не заново реализовывать настройки. Есть
также асинхронная обработка EPUB, кэш переводов и фоновый worker.

Но есть два подтверждённых пробела в текущей реализации:

1. `DELETE` книги проверяет лишь действительность токена. Любой вошедший
   пользователь сейчас может удалить любую книгу.
2. В системе нет ролей, а пароль проверяется на минимум 12 символов и на
   frontend, и на backend.

Сообщения «В книге нет доступных глав», медленный старт чтения и ошибки
переводчика нельзя надёжно исправить по одному симптому: у каждого есть
несколько возможных причин. Первым этапом будут воспроизводимые измерения и
логи без содержимого книг и персональных данных.

## 0. Контроль исходного состояния и измерения

Цель: получить воспроизводимые причины четырёх пользовательских проблем до
изменения схемы или оптимизаций.

1. Составить минимальный ручной сценарий для desktop и touch: открыть
   «Настройки текста», передвинуть оба ползунка клавиатурой, мышью и пальцем,
   сохранить, обновить страницу и проверить фактический размер/интервал.
2. На нескольких EPUB (короткой, длинной, с иллюстрациями) десять раз открыть
   книгу из каталога и личной библиотеки. Записать HTTP/gRPC-ответ
   `GetReadingState`, статус книги, число глав, размер возвращённой главы и
   время ответа. Отдельно отличить состояние `processing` от готовой книги с
   нулём глав.
3. Замерить время по участкам: получение состояния чтения, размер и время
   разбора главы в браузере, запрос словаря и запрос LibreTranslate. Добавить
   структурированные server-side метрики/логи длительности и результата,
   но не текст книги, перевод или токены доступа.
4. Проверить здоровье и холодный старт локального LibreTranslate, его язык
   `en → ru`, тайм-аут, ответы 4xx/5xx и попадания/промахи кэша на повторном
   переводе одного контекста.
5. Зафиксировать исходные показатели и целевые бюджеты после замера. Для
   маленького семейного сервиса достаточно p95 и количества ошибок; не нужно
   вводить Redis или отдельный сервис мониторинга.

Критерий готовности: для каждой из проблем есть один из статусов
«воспроизведена с причиной», «данных пока недостаточно» или «не
воспроизводится», а также исходные числа для сравнения после исправления.

## 1. Надёжное открытие книг и работа ползунков

Цель: готовая книга всегда открывается в устойчивом состоянии, а настройки
текста управляются доступными элементами формы.

1. Исправить frontend-состояние ридера: не показывать «В книге нет доступных
   глав» в промежутке между успешным ответом API и `useEffect`, который ещё не
   скопировал главу в локальное состояние. Пока локальная глава инициализируется
   — показывать загрузку; пустое состояние показывать только после
   подтверждённого ответа без главы.
2. На backend усилить инвариант `ready`: готовой может стать только книга с
   хотя бы одной главой в той же транзакции. Для старых некорректных записей
   вернуть понятную ошибку «книга обрабатывается/повреждена», а не пустой
   reader state; подготовить безопасную переобработку исходного EPUB.
3. По результатам этапа 0 устранить первопричину ползунков: проверить
   перекрывающий слой, `pointer-events`, фокус, нативный range-control и
   mobile-обработчики. Добавить явные стили дорожки/бегунка только если это
   необходимо для воспроизведённого браузера; сохранить keyboard-доступность
   и видимый focus.
4. Добавить frontend-тесты: изменение каждого range, сохранение и восстановление
   настроек; тест ридера на начальный успешный ответ с главой. Добавить
   интеграционный тест инварианта `ready` и тест переобработки старой книги.

Критерий готовности: 10 последовательных открытий каждой тестовой готовой
книги не дают ложного пустого состояния; оба ползунка меняются мышью, touch и
клавиатурой, сохраняются после перезагрузки и применяются к тексту.

## 2. Перевод: доступность и скорость

Цель: карточка слова остаётся полезной при проблеме провайдера, а повторные и
частые переводы не ждут лишнего времени.

1. На основе измерений определить, где задержка: холодный LibreTranslate,
   сетевой тайм-аут, очередь/конкуренция либо cache miss. Исправлять только
   подтверждённое узкое место.
2. Сохранить локальный словарь независимым от машинного перевода: senses и
   примеры показываются сразу, а перевод короткого контекста и полного
   предложения имеют самостоятельные состояния loading/error/retry.
3. Нормализовать ключ кэша (язык, версия модели и нормализованный текст),
   проверить срок жизни и добавить защиту от одновременных одинаковых запросов
   (single-flight). Это исключит несколько параллельных обращений при одном
   клике/повторном рендере.
4. Настроить ограниченный retry только для временных сбоев с короткой задержкой
   и отменой по закрытию модального окна. Не повторять ошибки запроса 4xx и не
   делать бесконечные ретраи. Сохранить circuit breaker, но показывать понятное
   состояние и возможность попробовать позже.
5. Если измерения покажут, что двухсекундный тайм-аут слишком мал для
   нормального локального перевода, согласованно изменить `TRANSLATE_TIMEOUT`;
   одновременно оставить ограничение длины текста и не увеличивать его без
   отдельного замера.
6. Добавить тесты hit/miss кэша, конкурентного одинакового запроса, timeout,
   4xx/5xx, отмены UI и ручной сценарий первого запуска модели.

Критерий готовности: повторный перевод одного и того же текста приходит из
кэша; временная ошибка не ломает карточку слова; нет дублирующих запросов;
время и доля ошибок после изменения лучше исходных показателей этапа 0.

## 3. Быстрое открытие длинных EPUB

Цель: пользователь начинает читать быстро, независимо от объёма всей книги.

1. По замерам выбрать причину: крупный `sanitized_html`, слишком тяжёлая
   обработка DOM/подсветки, медленная SQL-выборка или EPUB с чрезмерно крупными
   spine-документами. Сначала добавить `EXPLAIN ANALYZE` на тестовой БД и
   профилирование браузера; не менять индексы наугад.
2. Если глава слишком велика, расширить EPUB-parser: безопасно делить один
   spine-документ на читаемые фрагменты по блочным границам с заданным лимитом
   текста/размера ответа. Не разрывать внутри HTML-элемента, не терять
   изображения, ссылки и порядок чтения.
3. Сохранить прогресс при переобработке: прежде чем удалить старые главы,
   сопоставить позицию пользователя с устойчивым `href` и смещением/якорем;
   если точное сопоставление невозможно — открыть ближайший безопасный фрагмент,
   а не первую страницу молча.
4. Уменьшить фронтенд-работу только там, где это покажет профиль: не повторять
   декорацию/подсветку без изменения главы или словаря, не блокировать первый
   paint тяжёлыми операциями, корректно отменять устаревшие ответы при переходе
   между книгами.
5. Переобработать имеющиеся EPUB отдельной операторской командой после
   резервной проверки БД и файлов. Отслеживать `processing/ready/failed` и не
   считать такую книгу готовой до атомарного завершения.

Критерий готовности: тестовые длинные книги укладываются в согласованный
бюджет первого открытия, отображают первую доступную часть без пустой страницы,
не теряют изображения; пользовательский прогресс сохраняется при переходе и
переобработке.

## 4. Роли, право удаления и лимит загрузок

Цель: право определяется сервером и не обходится прямым HTTP/gRPC-запросом.

1. Ввести минимальную модель `user` и `admin`: миграция с ролью `user` по
   умолчанию для всех существующих и новых аккаунтов. Роль не выдаётся при
   регистрации и не меняется публичным API.
2. Создать безопасную операторскую команду назначения администратора по уже
   существующему email/ID, доступную только с доступом к БД. Перед применением
   команда выводит найденный аккаунт и требует явного подтверждения. Так
   первый администратор создаётся контролируемо, а не через скрытый пароль или
   переменную в frontend.
3. Добавить общий server-side policy/usecase для действий с книгами:
   `admin` может удалить любую и загружать без лимита; обычный пользователь —
   удалить только книгу, где `uploaded_by_user_id` равен его ID, и создать не
   более 10 существующих книг. Дубликат EPUB, который не создаёт новую запись,
   не должен расходовать квоту.
4. Проверять лимит и право внутри транзакции/запроса до записи или удаления,
   а не по данным, присланным клиентом. Возвращать отдельные ошибки
   `permission_denied` и `upload_limit_reached`, которые HTTP и gRPC отдают как
   403/понятный статус, а UI переводит в ясное русское сообщение.
5. Расширить контракт ответов книги/текущего пользователя минимальными
   признаками возможностей (`can_delete`, `can_upload` или эквивалент),
   перегенерировать proto-клиенты. UI показывает кнопку удаления только при
   наличии права, блокирует/объясняет лимит 10 и после каждой операции обновляет
   каталог и личную библиотеку. Серверная проверка остаётся обязательной.
6. Покрыть миграцию, обычного пользователя, владельца, другого пользователя,
   администратора, ровно десятую/одиннадцатую загрузку, параллельные загрузки,
   HTTP и gRPC. Отдельно проверить, что удаление из личной библиотеки по-прежнему
   лишь удаляет `user_books`, а не общую книгу.

Критерий готовности: пользователь не может удалить чужую книгу даже вручную
вызванным API; загрузивший может удалить свою; администратор может удалить
любую и не ограничен десятью; существующие пользователи безопасно становятся
обычными.

## 5. Пароль минимум 8 символов

Цель: правило одинаково во всех интерфейсах и на сервере.

1. Вынести минимум пароля в одну backend-константу/валидацию и изменить с 12
   на 8, сохранив верхний лимит и хэширование.
2. Изменить `minLength`, тексты ошибок и frontend-валидацию на 8. Логин не
   ограничивать этим правилом, чтобы существующие пароли не блокировались.
3. Добавить тесты для 7, 8 и 256+ символов через usecase и UI.

Критерий готовности: регистрация с паролем из 8 символов успешна, из 7 —
отклонена одинаковым понятным сообщением в браузере и API.

## 6. Точечные правки интерфейса

Цель: одинаковые карточки и доступные, ровно выровненные действия без
изменения утверждённого визуального направления сайта.

1. В кнопках переключения глав задать явный layout (`inline-grid`/`flex`),
   `place-items: center`, согласованные размеры и `line-height`; проверить
   desktop, mobile, keyboard-focus и масштаб браузера.
2. Привести `BookCard` и `MyBookCard` к одной структуре высоты: ограничить
   заголовок двумя строками с понятным ellipsis/tooltip, выделить фиксированную
   область метаданных/прогресса и прижать `.book-actions` к низу через flex/grid.
   Карточки с разными названиями, статусами и прогрессом не должны менять высоту
   кнопок в одной сетке.
3. В карточке перевода заменить нижнюю текстовую кнопку «В мой словарь» на
   иконку `+` в правом верхнем углу. Дать ей доступное имя
   `aria-label="Добавить в мой словарь"`, видимый focus и tooltip с тем же
   текстом при hover и keyboard-focus; во время сохранения/для уже сохранённого
   слова показать соответствующее недоступное состояние.
4. Добавить визуальные/component-тесты на длинные названия, карточки разных
   типов, tooltip, фокус и центрирование стрелок; провести ручную проверку
   touch-устройства.

Критерий готовности: стрелки визуально центрированы, ряды карточек ровные при
разных заголовках, добавление слова выполняется новой иконкой и остаётся
доступным с клавиатуры и скринридером.

## 7. Общая приёмка и документация

1. Прогнать backend unit/integration-тесты, миграции на пустой и существующей
   тестовой БД, `npm run lint`, frontend-тесты и `npm run build`.
2. Добавить Playwright-сценарии: регистрация с 8 символами; 10/11 загрузок;
   удаление владельцем/чужим/админом; многократное открытие книги; настройки
   текста; перевод с кэшем и недоступным провайдером; сохранение слова новой
   кнопкой; long-title карточки.
3. Повторить замеры из этапа 0 и записать сравнение до/после, включая известные
   ограничения конкретных EPUB и LibreTranslate при первом запуске.
4. Обновить `README.md` и `frontend/README.md`, если изменятся команды,
   переменные окружения, порты или интеграция. Описать операторскую команду
   выдачи admin-ролей в backend-документации без секретов.

Критерий готовности: автоматические проверки зелёные, миграция обратимо
проверена на тестовой копии, все пункты v1.2 подтверждены ручным сценарием,
а измеренные регрессии отсутствуют.
