# Backend session: 2026-09-03 / 01

## Назначение

Документ фиксирует все фактически внесённые в backend изменения на текущем
этапе. Сервис рассчитан на закрытое семейное использование, менее 50
пользователей, общий EPUB-каталог, личные библиотеки и бесплатный локальный
переводчик.

## Структура и запуск

Создан Go-модуль `github.com/deniskrylov/english-reader/backend` с требованием
Go 1.25. Основные entrypoints:

- `cmd/server` — API-процесс;
- `cmd/migrate` — применение и откат PostgreSQL-миграций;
- `internal/config` — конфигурация из окружения;
- `internal/database` — `pgxpool` и embedded migrations;
- `internal/transport/grpcserver` — gRPC transport;
- `internal/transport/httpserver` — служебный HTTP API, Auth REST API и Swagger;
- `internal/auth` — доменная логика и PostgreSQL-репозиторий аутентификации.

Созданы `Dockerfile`, `.env.example`, `.gitignore`, `Makefile` и
`docker-compose.yml`, а также `README.md` с инструкциями запуска, тестирования,
миграций и таблицей портов. Полный старт в development:

```bash
cd backend
cp .env.example .env
make infra-up
make migrate-up
make app-up
```

Основные Make-команды: `infra-up`, `infra-down`, `app-up`, `app-down`, `run`,
`migrate-up`, `migrate-down`, `test`, `test-race`, `test-docker`, `fmt`, `vet`,
`tidy`, `proto-lint`, `logs`, `ps`.

Compose описывает:

### Исправленные проблемы Docker

1. LibreTranslate завершался с `PermissionError` при записи в
   `/home/libretranslate/.local/share/argos-translate`. Причина — volume был
   смонтирован в подкаталог, созданный Docker с неподходящими правами.
   Исправление: volume монтируется в `/home/libretranslate/.local:rw`, добавлены
   `LT_UPDATE_MODELS=true` и `LT_THREADS=4`.
2. Порты `5432` и `8080` были заняты другими локальными процессами. Чтобы не
   останавливать чужие сервисы, default ports перенесены на `5433` и `8082`.
   Они переопределяются через `POSTGRES_PORT` и `ENVOY_PORT` в `.env`.
3. Для доступа к HTTP API и Swagger с хоста добавлен development mapping
   `API_HTTP_PORT=8083`.

После исправлений проверено, что `postgres` имеет статус `healthy`, а
`libretranslate`, `api` и `envoy` работают.

## PostgreSQL и миграции

База подключается через `github.com/jackc/pgx/v5/pgxpool`. Пул проверяет
соединение при старте, использует максимум 10 соединений и минимум 1.

Добавлена начальная миграция
`internal/database/migrations/000001_initial.{up,down}.sql`. Она создаёт:

- `users`, `auth_sessions`;
- общий EPUB-каталог: `books`, `book_chapters`, `ingestion_jobs`;
- личную библиотеку: `user_books`;
- ридер: `reading_progress`, `user_reader_settings`;
- словарные данные: `dictionary_lemmas`, `dictionary_senses`,
  `vocabulary_entries`, `translation_cache`, `dictionary_import_runs`.

Важные ограничения схемы:

- `books.format` допускает только `epub`;
- `books.content_sha256` уникален для будущей дедупликации файлов;
- `user_books` имеет составной первичный ключ `(user_id, book_id)`;
- `reading_progress` ссылается на эту связь, поэтому прогресс невозможен для
  не добавленной пользователем книги;
- email хранится как уникальный `citext`;
- refresh-token хранится как `BYTEA` hash, а не в открытом виде.

## gRPC и HTTP-инфраструктура

gRPC запускается на `:9090`, включает стандартные gRPC Health и Server
Reflection, structured logging interceptor и panic recovery interceptor.
Envoy из `deployments/envoy/envoy.yaml` преобразует browser gRPC-Web трафик в
обычный gRPC и разрешает development origin `http://localhost:5173`.

HTTP-слой использует роутер `chi` и предоставляет:

- `GET /health/live`;
- `GET /health/ready` — дополнительно проверяет PostgreSQL;
- `GET /openapi.yaml`;
- `GET /swagger/index.html` — Swagger UI;
- REST-маршруты `/api/v1/auth/*`.

Swagger-спецификация находится в `internal/transport/httpserver/openapi.yaml`
и встраивается в бинарник через `go:embed`.

## Обязательная архитектура запросов

`AGENTS.md` дополнен обязательным для всех новых backend-запросов правилом:

```text
handler → request-specific usecase → optional reusable service → repository
```

Для каждого HTTP/gRPC запроса создаются собственные файл и Go package handler,
а также отдельный package usecase. Handler не вызывает repository напрямую;
usecase содержит сценарий и авторизацию; service появляется только для логики,
переиспользуемой несколькими usecases; repository занимается только данными.
Все эти слои находятся в разных пакетах. Конкретные зависимости собираются
только в `cmd/server`.

Каждый package usecase и service обязан иметь `dependencies.go`: в нём
объявляются минимальные интерфейсы зависимостей, потребляемые этим пакетом.
Интерфейсы также могут быть в `handler/dependencies.go`, если handler нужно
абстрагировать usecase. Конструкторы usecase, service и repository всегда
возвращают concrete type (`*UseCase`, `*Service`, `*Repository`), а не свой
интерфейс; интерфейс объявляет и принимает пакет-потребитель.

## AuthService

Добавлен gRPC-контракт `protos/reader/v1/auth.proto` и сгенерированный Go-код в
`gen/reader/v1`. Методы gRPC:

- `Register`;
- `Login`;
- `Refresh`;
- `Logout`;
- `GetMe`.

REST API предоставляет эквивалентные endpoints:

| Endpoint | Поведение |
| --- | --- |
| `POST /api/v1/auth/register` | Создаёт аккаунт и сессию, возвращает access token, ставит refresh-cookie. |
| `POST /api/v1/auth/login` | Проверяет пароль и создаёт новую refresh-сессию. |
| `POST /api/v1/auth/refresh` | Находит валидную cookie, отзывает старую сессию и создаёт новую. |
| `POST /api/v1/auth/logout` | Отзывает текущую refresh-сессию и очищает cookie. |
| `GET /api/v1/auth/me` | Возвращает пользователя для Bearer access JWT. |

Реализованные меры безопасности:

- пароль проверяется на длину 12–256 символов и хранится Argon2id hash;
- access JWT подписывается HS256, содержит subject, issuer, `iat` и `exp`;
- `JWT_SECRET` обязателен и должен содержать не менее 32 символов;
- refresh-token генерируется криптографически, в БД помещается SHA-256 hash;
- refresh token передаётся HTTP-клиенту только как `HttpOnly`, `SameSite=Strict`
  cookie; `Secure` включается вне `APP_ENV=development`;
- одинаковый email приводит к `409`, неверные credentials/token — к `401`;
- JSON decoder запрещает неизвестные поля и ограничивает размер body.

Конфигурация auth: `JWT_SECRET`, `ACCESS_TOKEN_TTL` (по умолчанию `15m`),
`REFRESH_TOKEN_TTL` (по умолчанию `720h`).

## Рефакторинг Auth под request architecture

Auth-код приведён к обязательной цепочке
`handler → usecase → optional service → repository`.

- Для REST и gRPC каждый из запросов `register`, `login`, `refresh`, `logout`
  и `getme` получил отдельный package handler. gRPC transport теперь лишь
  объединяет готовые handlers для сгенерированного `AuthService`.
- Каждый сценарий вынесен в отдельный package usecase:
  `internal/usecase/auth/<request>/`. В каждом есть `dependencies.go` с
  минимальными интерфейсами потребляемых зависимостей.
- Повторяемая криптографическая логика разделена на concrete services
  `password`, `token` и `refreshtoken`, каждый со своим `dependencies.go`.
- PostgreSQL-операции Auth сосредоточены в concrete repository
  `internal/repository/postgres/auth`; его конструктор возвращает
  `*Repository`.
- HTTP-ответы и gRPC-маппинг ошибок вынесены в transport-вспомогательные
  пакеты, чтобы handlers не зависели друг от друга.
- `cmd/server` стал единственной composition root: только там создаются
  concrete зависимости и передаются в конструкторы.

## LibraryService MVP

Реализованы REST-сценарии общего каталога и личной библиотеки:

- `POST /api/v1/library/books` принимает multipart-поле `file`, требует Bearer
  JWT, допускает только `.epub`, проверяет ZIP magic bytes, ограничивает размер
  50 MiB, сохраняет оригинал в закрытом book volume и дедуплицирует по SHA-256;
- `GET /api/v1/library/books` и `GET /api/v1/library/books/{bookID}` выдают
  общий каталог без файловых путей;
- `POST`/`DELETE /api/v1/library/books/{bookID}/my-library` и
  `GET /api/v1/library/my-books` реализуют идемпотентную личную библиотеку с
  курсорной пагинацией. Добавление разрешено только для `READY`.

Добавлен `reader/v1/library.proto` и `make proto`: команда генерирует Go и
gRPC-код для всех контрактов из `protos/reader/v1`.

Добавлен локальный DictionaryService: versioned JSONL importer с атрибуцией,

## VocabularyService и подсветка

Добавлен отдельный `reader/v1/vocabulary.proto` и gRPC-Web-совместимый
`VocabularyService` с методами `SaveEntry`, `ListEntries`, `DeleteEntry` и
`GetHighlights`. Для каждого метода созданы самостоятельные gRPC handler и
usecase согласно request architecture.

- `SaveEntry` принимает только dictionary lemma ID, проверяет выбранный sense и
  делает сохранение идемпотентным через `(user_id, lemma_id)`;
- `ListEntries` поддерживает нормализованный поиск и cursor pagination;
- `DeleteEntry` удаляет запись только текущего subject и безопасен при повторе;
- `GetHighlights` читает только server-side `plain_text`, токенизирует слова с
  Unicode apostrophe, применяет best-effort morphology и exact fallback.

Для подсветки репозиторий сначала проверяет связь пользователя с книгой через
`user_books`, затем статус `READY` и принадлежность главы книге. Поэтому
пользователь не может получить текст или совпадения из чужой личной библиотеки.
Ответ содержит только lemma, тип совпадения и позиции; XHTML, полный текст
главы и чужие записи в него не попадают. Размер текста, число lemmas и число
совпадений ограничены в usecase/service wiring.

Добавлены GoMock-тесты handlers, usecases и tokenizer, а также PostgreSQL
integration tests в `test/integration/vocabulary_repository_test.go`. Команда
`make test-repository` поднимает изолированную tmpfs PostgreSQL на `5434`.

## Закрытие функциональных gRPC-доработок

`LibraryService` зарегистрирован в gRPC server и теперь предоставляет
`ListCatalog`, `GetBook`, `AddToMyLibrary`, `ListMyBooks` и
`RemoveFromMyLibrary` через отдельные handlers. Добавлен native gRPC client-streaming
`UploadBook`: первое сообщение содержит JWT и имя файла, последующие передают
EPUB chunks в существующий upload usecase через `io.Pipe`, без полного файла в
оперативной памяти. Browser gRPC-Web не поддерживает client-streaming, поэтому
frontend использует существующий HTTP multipart upload; HTTP library API также
остаётся Swagger-compatible fallback.

В `DictionaryService.LookupWordResponse` добавлено `already_saved`. Lookup
получает ID lemma из dictionary repository и проверяет только
`(current_user_id, lemma_id)` в vocabulary repository, поэтому карточка может
сразу показать состояние кнопки добавления без утечки записей других членов
семьи.

Добавлена [инструкция импорта словаря](../DICTIONARY_IMPORT.md): production
dump выбирает оператор, а source/version/checksum и attribution фиксируются
при versioned JSONL import. Тестовый мини-набор явно обозначен как development
fixture.
